# Brand-new cross-account BYO Shop setup

This procedure targets a **new blank Shop**, not Client 1 (`kxmovywgshyltwusghhj` / `orbito-client-1`). Nothing here resets a database or changes accounting cutover. Manual confirmed Auth creation is the default; SMTP and invitation delivery are optional.

## The three inputs

1. The new Shop's 20-letter project ref, with authorised access to that project.
2. `orbito-shop-pairing.env`, downloaded from that client's Platform setup guide.
3. A private `shop-runtime.env` containing the Shop's **server-side** `TURNSTILE_SECRET`.

Keep both files outside Git repositories (for example, your Downloads/private setup folder). Do not paste their contents into chat, issue trackers, Platform, terminal history or screenshots. Pairing contains two distinct opaque bridge credentials and the Platform bridge endpoint. It contains no Shop service key, DB password, customer Supabase password, secret API key or customer PAT. The local operator's CLI authentication stays local.

## Configure the browser and server separately

| Group | Names | Location / requirement |
|---|---|---|
| Shop browser | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON`, `VITE_TURNSTILE_SITE_KEY` | Cloudflare Pages build settings; own Shop URL and public anon key plus public CAPTCHA site key; required |
| Legacy usage compatibility | `VITE_CLIENT_ID`, `VITE_PLATFORM_URL`, `VITE_PLATFORM_ANON` | Public build values; needed only if retaining legacy usage delivery. Fresh V2 uses the secure bridge binding, not these values for ownership/discovery |
| Supabase built-ins | `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` | Supplied inside Shop Edge runtime by Supabase; never collect or install through Platform or a VITE variable |
| Pairing | `PLATFORM_BRIDGE_CALL_SECRET`, `PLATFORM_BRIDGE_SOURCE_SECRET`, `PLATFORM_BRIDGE_ENDPOINT` | Shop Edge secrets; generated by Platform, installed through the sensitive download |
| Application runtime | `TURNSTILE_SECRET` | Shop Edge secret; same real CAPTCHA widget as the browser site key, with the Shop hostname allowed |
| Optional support login | `PLATFORM_SUPABASE_URL`, `PLATFORM_SUPABASE_ANON`, `PLATFORM_AUTH_EMAIL` | Shop Edge secrets only if support mode is intentionally enabled; supply all three or omit all three. Normal Shop login is independent |

The runtime file accepts only `TURNSTILE_SECRET` and the optional three support settings, with unquoted `NAME=value` lines. Unknown names, including privileged customer keys and VITE variables, are rejected. Values are never printed. Neither `TURNSTILE_SECRET` nor any service key, bridge secret, DB password or PAT belongs in a `VITE_*` variable.

Platform's browser uses `VITE_PLATFORM_URL`, `VITE_PLATFORM_ANON`, and **`VITE_TURNSTILE_KEY`** (different name from the Shop). The canonical master identity is the **existing server-authorized Supabase Auth UUID**; its current email comes from Auth. `platformadmin@retailos.internal` is a historical SQL authorization literal/test fixture, not the current hosted master email, not an Auth seed and not an account that must be created. The new `platform_operator_identity()` delegates to the existing deployed `platform_private.operator_role()`; checkpoint migrations preserve that function and the working UUID authorization.

`platform_config.admin_username` is only a display/login alias. `VITE_PLATFORM_AUTH_EMAIL` supplies the Auth email destination for alias login; it must match the existing master's actual current Auth email if aliases are used. It grants no role, does not create/change Auth users, and is unnecessary for actual-email login or session restoration. Preserve the correct hosted build setting on upgrade; a stale local alias-email value is not proof of hosted identity. Changing the alias does not change the UUID/email; alias edits reauthenticate using the verified current Auth email. Reset uses the entered Auth email; password changes use Auth `updateUser`, with no application-table password writes. The baseline's dormant `admin_password` column/default is historical, not an active credential; browser read/write ACLs exclude it. Never populate it with an Auth password.

## Exact sequence

1. Create the new blank Supabase project under the customer's account. Record its ref; verify it is not Client 1 or the Platform project. Do not create the owner Auth account yet.
2. Reserve a Cloudflare Pages project/hostname (or a chosen custom Shop hostname). You can know this URL before deploying the Shop. Add Client in Platform using that URL, owner name/exact email, plan, rates/currency, Inventory, Paper Resupply and independent Break Tracking selection; choose **client-owned/BYO**. Client Detail displays/copies the resulting Client ID. No runtime client discovery is needed.
3. Work in the Shop repository on `feature/onboarding-v2`. Use the reviewed release containing the complete migration chain through `20261001120000_onboarding_runtime_preflight.sql`. Do not copy only the two latest migrations to a blank database.
4. Have the authorised project owner/operator connect this Shop repository to the **new project** using Supabase's GitHub integration, select the reviewed branch/release as the deployment branch, and enable production migration deployment for that new project. Confirm all migration versions were applied in order in the project's deployment/history view. The source includes the neutral Shop baseline, private config/RLS, identity/usage/bridge/PIN, V2 reservation/manual activation, and runtime grants/preflight. Keep seed/customer data out. This is a guided migration release step, not `--include-all`, remote reset or a SQL-editor paste that loses migration history. If Git integration is unavailable, arrange an approved project-owner migration release before continuing; the setup tool deliberately does not solicit a DB password. See [Supabase production deployment](https://supabase.com/docs/guides/deployment/going-into-prod) and [migration workflow](https://supabase.com/docs/guides/local-development/database-migrations).
5. Obtain temporary authorised project access, use screen sharing with the owner, or use an authorised operator's own local Supabase CLI account. Run `supabase login` locally if needed; the customer handles their own sign-in. Use an official installed Supabase executable (`supabase.exe`/Scoop shim on Windows), not a shell wrapper. `--cli` accepts an executable path if needed. Check `supabase --version`, `supabase functions deploy --help` and `supabase secrets set --help`; the tool also checks the needed flags.
6. Run `supabase projects list --output json`. Confirm the **new ref** is visible in the current account. Visibility alone does not prove write permissions; secret installation/deployment must also succeed. An account that cannot see/manage the project needs correct temporary access before continuing.
7. Client Detail → **Complete BYO Setup** → Download pairing file. Save it outside both repositories. Verify the path exists. Download again from the intended client if target metadata does not match; never edit its generated credentials.
8. Create the private runtime file outside the repositories using a local editor: `TURNSTILE_SECRET=<the real server-side widget secret>`. Do not echo the secret into a command. Add the optional support group only if intentionally enabling support mode.
9. Validate local branch, file names/target metadata, permitted settings, CLI flags and account visibility without hosted writes:

```powershell
npm run byo:setup -- --project-ref NEW_SHOP_REF --pairing-file "$env:USERPROFILE\Downloads\orbito-shop-pairing.env" --runtime-file "$env:USERPROFILE\Downloads\shop-runtime.env"
```

10. After the approved full migration release, install/deploy/verify using the same inputs:

```powershell
npm run byo:setup -- --project-ref NEW_SHOP_REF --pairing-file "$env:USERPROFILE\Downloads\orbito-shop-pairing.env" --runtime-file "$env:USERPROFILE\Downloads\shop-runtime.env" --apply --remove-pairing
Test-Path "$env:USERPROFILE\Downloads\orbito-shop-pairing.env"
```

The final command must return **False** after successful removal. On other operating systems, supply their absolute local paths. The tool installs application runtime and pairing separately, deploys exactly `login`, `account-admin`, `verify-pin`, `password-reset-request`, `public-track`, `platform-bridge` using server-side API bundling, and calls the protected runtime preflight. It suppresses raw CLI output, prints named progress/check failures, retains the pairing file on failure, and deletes it only after success when explicitly requested. Removal is a filesystem unlink, not forensic erasure; remove additional browser downloads/backups and delete the private runtime file when no longer needed. Existing Supabase function JWT settings are preserved: only the opaque-credential bridge disables gateway JWT. [CLI deployment and secret flags](https://supabase.com/docs/reference/cli/supabase-functions-deploy).

11. Configure the Shop's three public build variables and deploy to the reserved Cloudflare hostname. If legacy usage values are retained, the Client ID is already available from step 2; configure those public values before deployment/redeployment. Do not alter usage semantics. Verify Pages serves `/login`, `/onboarding`, and optional `/invite/accept` via the SPA fallback. Use a real CAPTCHA site key/server secret pair with this hostname permitted. Test keys are for local validation only. [Cloudflare CAPTCHA testing](https://developers.cloudflare.com/turnstile/troubleshooting/testing/).
12. Platform → **Provision Shop / Reserve owner**. Platform registers the immutable source, sends the existing billing/module projection, then refreshes Shop runtime status. Infrastructure remains pending if any required backend check fails. If a recorded attempt failed, fix setup and use **Retry Provisioning** / Advanced → Retry recorded operation; do not create a replacement client/reservation.
13. When the backend checks are ready, an authorised operator uses that Shop's Dashboard → Authentication → Users to create **one confirmed user** with the exact reserved normalized owner email and a password handled only there. Do not insert `app_users`/employees manually, use a second owner email or overwrite an existing invitation identity. Check existing Auth before retrying an unknown account creation outcome.
14. Platform → **Check Owner Account**. A confirmed Auth account is shown as waiting for owner login, an unconfirmed account as unconfirmed, and a conflicting identity needs reconciliation. Creating Auth alone does not activate the owner.
15. Owner opens Shop Login, completes the real CAPTCHA and signs in. The verified Shop session calls no-argument `activate_reserved_owner()`; exact reserved email/UUID, confirmation, no conflict and suspension checks produce one Active Business Owner with `employee_id=NULL` and no employee row.
16. Complete all six saved steps: business/branding (PNG/JPEG/WebP ≤512 KB inline logo), contact, receipt/tax, separate override PIN, read-only plan features, review/complete. Logo uses the protected `shop_config` path; no bucket, storage object path or extra storage policy is required. Sign out/resume later reloads saved values; it starts at step 1 to review rather than inventing an unsaved progress record. Completion checks required fields/PIN/verified owner and sets `onboarding_completed_at`; normal dashboard then opens.
17. Refresh Platform owner/runtime status. Verify the plan, independent Inventory and Paper Resupply, printing with paper off, bridge delivery, and Client 1 unchanged. Optional invitation is secondary and only explicit; verify email delivery/SMTP/redirects separately if using it.

## What “ready” proves and what still needs a hosted smoke check

Backend readiness requires the current runtime contract, full DB/RPC/sequence/private-config ACL checks, actual service-client config read, all five normal function probes plus the protected bridge, required runtime values, working Shop Auth Admin API, matching V2 owner reservation/binding, distinct bridge credentials, bridge mode and an applied Shop configuration projection. Only fixed booleans and owner-account state leave Shop. Supabase's customer service key stays inside Shop.

Presence of a CAPTCHA secret cannot prove that it matches the browser site key/hostname. Local mocks cannot prove live CAPTCHA validation, Supabase email confirmation/SMTP/invites/redirects, hosted JWT gateway/signing-key behavior, Vault encryption, Management API permissions, Git integration release behavior, cross-account grants, DNS/TLS or Cloudflare SPA routing. Verify those on the new project. Overall readiness is a timestamped backend observation, not a guarantee about every external provider or subsequent configuration change.

The code is reviewed locally; this procedure must use an approved published release before the next hosted test. This development pass made no hosted migration, deployment, secret change, commit or push.
